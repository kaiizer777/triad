# Triad DB (Persistence) — Mini Skill

You already have the full `db` skill in this session (Main was
injected earlier). This is the condensed pointer version.

Triad has **no SQL database today**. The "db" section here covers
the JSONL persistence Triad actually has, plus a one-screen
pointer to the conventions a future real DB should follow.

## What's persisted, and where

- **Session transcript** —
  `internal/loop/sessions/<session-id>.jsonl`. One JSON object
  per line, shape `internal/transcript.Entry`:
  ```go
  type Entry struct {
      ID, Speaker, Type, Content string; Timestamp time.Time
  }
  ```
  Append-only. Never rewritten.

- **Per-session trace log** —
  `internal/loop/sessions/traces/<session-id>.jsonl`. Structured
  EventType-keyed events for `/trace`. EventType is a string
  enum in `internal/tracelog/`. New event types: add the
  constant in `tracelog`, never write to the trace JSONL
  directly.

- **Git history** — every approved Coder action triggers a
  per-action `git commit` (see `internal/gitcommit/`). `/undo`
  reverts, `/summary` reads the local commit log (not the LLM).

## Conventions — apply to anything you write to disk

1. **Append-only, always.** `transcript.Transcript.Append` and
   `tracelog.Append` are the only writers. To correct, append a
   new entry referencing the prior ID — don't edit history.
2. **One JSON object per line.** Compact `json.Marshal`, never
   pretty-print.
3. **Stable field order.** Marshal the same struct shape; never
   construct `map[string]any` for entries.
4. **Time is `time.Time` UTC.** Every `Timestamp` goes out as
   UTC. Localized timestamps break `/trace` ordering across
   timezones.
5. **IDs are monotonically increasing per session.** Set by
   `transcript.Transcript` as a per-session counter. Don't set
   manually.
6. **Speaker is one of the four constants** in
   `internal/transcript/entry.go`: `SpeakerYou`,
   `SpeakerCoder`, `SpeakerReviewer`, `SpeakerSystem`. New
   type? Add a constant.
7. **Type is `"message"`, `"proposed_action"`, or
   `"action_result"`.** New type? Add a constant.

## Trace log vs transcript

- **Transcript** = human-readable session replay, model-facing
  surface. Use for things Coder/Reviewer need to see.
- **Trace log** = structured observability for `/trace` and
  programmatic consumers. Use for events with fields (tool
  proposed, reviewer verdict, skill selection, commit
  records). NOT model-facing.

## File path conventions

- Session files: `internal/loop/sessions/<session-id>.jsonl`.
  ID is generated by the loop; don't construct by hand.
- Trace files: `internal/loop/sessions/traces/<session-id>.jsonl`.
  Path via `tracelog.TracePathForSession(sessionPath)`.
- Both are in `.gitignore` — runtime artifacts, not source.

## Crash safety

Triad flushes after every append. A crash mid-turn may lose
the most recent un-flushed entry but won't corrupt the file.
Replay-on-startup is robust to truncated trailing lines
(partial write → treat as in-progress, don't truncate-and-
rebuild; if needed, append a `[System]: recovered from
partial write at line N` entry).

## When a real DB shows up (template)

If/when a real DB is added (Postgres, SQLite, etc.), the
conventions to follow:

### Schema

1. **One append-only event table** — even for a relational DB.
   Materialized state is a projection, not the write target.
2. **`timestamptz` (Postgres) or INTEGER Unix-epoch
   seconds (SQLite)**. Never `TIMESTAMP WITHOUT TIME ZONE`.
3. **IDs are UUIDs/ULIDs**, not auto-increment integers.
   Auto-increment couples writer order to ID generation.
4. **FKs are advisory.** Write path must be tolerant of
   missing FK target (the referenced event may not be
   replayed yet).
5. **Migrations in `migrations/`** with numeric prefix
   (`0001_init.sql`, …). Single up-file per migration.
   No down migrations.

### Connection / pooling

1. **One `*sql.DB` per process, shared.** Don't open a new
   connection per call.
2. **Starting pool:** `SetMaxOpenConns(25)`,
   `SetMaxIdleConns(5)`, `SetConnMaxLifetime(5*time.Minute)`.
   Tune from `pg_stat_activity`, not guesses.
3. **Every query has a context.** `db.QueryContext(ctx, ...)`,
   not `db.Query(...)`. The loop can be cancelled by human
   override; the DB call must be too.
4. **Time-bounded queries.** `context.WithTimeout(parent,
   2*time.Second)` for fast reads, longer for writes.
   Triad is interactive — long queries are UX bugs.

### Querying

1. **Named parameters** (`sqlx.Named` / `sql.Named`) — never
   `fmt.Sprintf` a query.
2. **`SELECT` only the columns you read.** Don't `SELECT *`
   in a hot path.
3. **`EXPLAIN ANALYZE` before adding a new index.** Triad's
   session volume is small (one process, one human) — most
   "we need an index" instincts are premature.
4. **Batch writes** for backfills (staging table + `COPY` for
   Postgres, multi-row `INSERT` for SQLite). Single-row
   INSERTs in a loop are a code smell.

### Testing

1. **Test against a real DB in CI**, not a mock. SQLite
   in-memory for most tests; containerized test for
   Postgres-specific behavior. Never ship a `*MockDB` and
   call it "tested."
2. **Each test gets a fresh schema** via `TestMain` running
   migrations. No shared dev DB.
3. **Events table is append-only in tests too.** If a test
   "needs to update", append a corrective event and read the
   projected view.

## Common pitfalls (all hit at least once)

- Editing a transcript line in place to "fix" a typo —
  append a `[System]: correcting entry #N ...` line instead.
- Writing to `internal/loop/sessions/traces/default.jsonl`
  without a bound session — cross-session pollution. Use
  `tracelog.TracePathForSession(sessionPath)`.
- Using `time.Now()` without UTC for `Timestamp` — breaks
  cross-timezone ordering. Use `time.Now().UTC()`.
- Constructing entries as `map[string]any` — non-deterministic
  field order produces subtly different files. Marshal the
  struct.
- Forgetting `.gitignore` for new persistence paths under
  `internal/loop/sessions/` — runtime artifacts committed
  by accident bloat the repo.
- Pretty-printing JSON for "human readability" — file
  3-4x larger, breaks per-line parsing. Compact marshal only.
- Calling `json.MarshalIndent` on a struct that embeds
  `time.Time` — Go's pretty-printer can escape the `:`
  in the timezone offset inconsistently. Test the on-disk
  shape with `cat | jq` before committing the format.
- Forgetting to flush the writer. `bufio.Writer` over
  `*os.File` doesn't flush on every write; the existing
  code calls `Flush` after every `Append`. Match that
  pattern; if you batch, add `defer Flush` and document
  the window.
- Reading the trace log into memory all at once —
  `/trace` should stream entries, not slurp. Long
  sessions can have tens of thousands of trace events;
  slurping freezes the TUI on open.
- Storing "elapsed_ms" or "duration_s" in the Data
  struct — store the timestamp, let the consumer
  compute the diff. Replay-stays-correct.
- Schema drift in trace Data structs. Once a JSON
  field name is in the JSONL, it's a contract with
  every future consumer. Renaming requires a
  migration. Lock the wire shape with explicit
  `json:"..."` tags.

## Quick reference — what goes where

| Concern | Lives in | Format | Append? | Gitignored? |
| --- | --- | --- | --- | --- |
| Session replay | `internal/loop/sessions/<id>.jsonl` | one JSON object per line, `transcript.Entry` shape | yes | yes |
| Structured observability | `internal/loop/sessions/traces/<id>.jsonl` | one JSON object per line, `tracelog.Entry` shape | yes | yes |
| What code changed | git history (per-action commits) | `git commit` per approved action | yes (immutable) | no (source) |
| Skill / config content | `skills/`, `commands/`, `config.yaml` | markdown + YAML | no (edited) | no (source) |
| Logs | `triad.log` | structured logger | yes (rotated externally) | no |

If the task says "find out what X said at turn 17," read
the session JSONL. If it says "why did Coder pick
skill Y," read the trace log. If it says "undo the
last edit," read the git history. The three answer
different questions; resist the urge to consolidate.

## Sizing at a glance

- Transcript: 50-200 entries/turn × 1-5 KB/entry ×
  20-50 turns ≈ 2-10 MB per session for a typical
  task. Heavy sessions hit 50-100 MB.
- Trace log: 5-20 events/turn × 200-500 bytes/event
  — usually larger than the transcript in bytes
  because of the structured-payload repetition.
- Git history: bounded by the number of approved
  Coder actions. Per-action commit granularity is
  the right size for `git revert` precision; bigger
  commits break `/undo`'s single-action contract.

## When in doubt

If you're about to add a new persistence path, ask:

1. **Is this model-facing or human-facing?** Model-
   facing → transcript. Human/programmatic
   observability → trace. Both? Append to both, with
   the trace carrying the structured payload and the
   transcript carrying the human-readable summary.
2. **Is this runtime data or source?** Runtime data
   goes under `internal/loop/sessions/` (gitignored).
   Source code goes to git. Don't mix.
3. **Is the on-disk shape append-only?** If not,
   the wrong shape — the persistence model is
   append-only end to end. The right answer to
   "I need to update" is "append a corrective
   entry."
4. **Is the time in UTC?** If not, fix it before
   the file gets a single write.

If the answer to any of these is "I don't know,"
stop and read the relevant section of the Main
skill before writing code.

## What this skill does NOT cover

- TUI rendering, keybindings, layout, sidebar — `frontend`
  skill.
- Agent loop, approval flow, Reviewer config, subagent
  mechanics — `backend` skill.
- The actual content of the JSONL files (transcript
  message text, action proposals). Read those directly
  when needed; this skill is about the *format* and
  *conventions*, not the values.

If the task is "read line 47 of session XYZ", the answer
is `jq` on the file directly — not a skill lookup. Use
this skill when *adding* a new persistence path,
*changing* the schema, or *building* a new consumer
(e.g. a `/sessions` command).
